# Frozen-controller motor cutoff

Status: firmware requirement and evidence review; no actuation or watchdog GPIO is configured by the present bring-up image. Reserve **GPIO16 for WDI**, replacing the optional service UART TX proposal. Native USB remains the primary debug/programming interface.

The portable core intends a 10 ms control period and rejects the **next invocation** after a gap greater than 50 ms. A stopped task cannot make that invocation, disable a physical GPIO or cancel a free-running PWM peripheral. Driver current regulation at approximately 3 A limits current but does not establish a safe continuous stall duration.

## Required physical boundary

Propose an external, independently timed watchdog with **no more than 100 ms worst-case** from the last valid control heartbeat to the driver being disabled. Aim for a nominal setting around 50–70 ms only if component/timing-capacitor tolerance, voltage, temperature and propagation delay keep the guaranteed maximum below 100 ms. This is a design target, not a measured or certified cutoff. At the illustrative 30 mm/s fabric speed, 100 ms permits 3 mm of commanded travel plus the real stopping/coasting distance. Jam force, energy and safe mechanical stopping distance remain bench measurements.

The watchdog output should directly gate driver nSLEEP with the MCU's requested motor permission; resetting MCU EN is useful recovery in addition to that hardware cutoff. Do not rely on a reset pulse alone as proof that motor pins became safe. Once expired, the gate must remain safe through reset and boot. A watchdog whose output deasserts automatically after a fixed pulse must not allow a still-high motor permission to re-enable the driver before a verified reset/default-off state. The board implementation must demonstrate this sequence on an oscilloscope, including MCU held in reset and a deliberately frozen PWM task.

Only the motor control task may toggle WDI, once after a complete iteration has validated current sensor/reference/power state, checked the lease, computed bounded output and applied it. Do not feed WDI from a free-running PWM/timer/ISR, networking worker, idle loop or generic 'application alive' task. Those can continue after the control task stops. A windowed watchdog can additionally detect overly fast feeding if its timing fits the control-loop jitter, but does not replace correct ownership.

Idle/deep sleep must not produce periodic reset loops. Watchdog enable and default-state wiring require a board truth table: driver disabled whenever watchdog supervision is inactive; a controlled enable/feed sequence before motor permission; no motor permission during boot, flashing, updates or debug breaks. Changing the watchdog policy for OTA is permitted only after the motor output is physically disabled and stationary state is verified. Hardware fault/STOP authority must not wait for HA or radio work.

## Why default C6 watchdog settings are insufficient

ESP-IDF's task watchdog normally prints diagnostics and continues unless panic is configured. The interrupt watchdog first enters a panic path; a later stage is the hardware fallback. OpenOCD disables task/interrupt watchdog hardware at breakpoints and does not automatically restore it. These defaults do not prove the proposed 100 ms cutoff. A dedicated control-task user subscription is useful diagnostic defense, but other task feeds and debugger behavior must be understood. [C6 watchdog documentation](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-reference/system/wdts.html)

The exact v5.5.4 timer-group implementation sets stage 0 to interrupt and stage 1 to `WDT_STAGE_ACTION_RESET_SYSTEM`; its timeout handler feeds the hardware watchdog before normal timeout handling. A serviced stage-0 interrupt can therefore prevent the fallback stage. A configuration must be assessed as a full path, including interrupt/panic/logging/reset behavior, not just by reading the stage-1 constant. [ESP-IDF timer-group watchdog source](https://github.com/espressif/esp-idf/blob/v5.5.4/components/esp_system/task_wdt/task_wdt_impl_timergroup.c)

The C6 API documentation says `esp_restart()` resets CPUs but leaves most peripherals unreset. Do not equate a software restart with asynchronous reset of GPIO routing and MCPWM. [C6 system API](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-reference/system/misc_system_api.html#_CPPv411esp_restartv)

The C6 TRM v1.2, pages 304–306 and 546–547, distinguishes CPU, core and system reset. A hardware **core reset** covers HP peripherals and digital GPIOs; **system reset** adds the LP domain. MWDT supports core reset, whereas RWDT also supports system reset. Thus an explicitly configured hardware core-reset stage could provide a cutoff for the proposed HP-domain motor outputs. The remaining proof is the real register configuration, watchdog clock/stage timing, SDK ownership and debugger interaction, followed by fault injection. The HAL name `RESET_SYSTEM` must not obscure the chip-specific TRM distinction. An external gate makes motor disable independent of SDK panic policy and MCU execution. [C6 TRM, reset and watchdog chapters](https://documentation.espressif.com/esp32-c6_technical_reference_manual_en.pdf)

Acceptance includes frozen control task with working radio, all interrupts disabled, endless ISR, flash-cache stall, panic, brownout/reset, native USB debug halt, WDI stuck high/low, and watchdog timeout followed by release. Measure nSLEEP and motor terminals together, and prove no spontaneous restart. This is a focused physical fault-injection requirement; the host core's tests cannot prove it.
