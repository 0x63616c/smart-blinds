# Control-task heartbeat sequence

Status: portable policy and host tests only. `firmware/include/smart_blinds/heartbeat.hpp` writes no GPIO, configures no PWM and is not connected to either C6 evaluation image. The captured supervisor and real board still need the physical fault tests in [the cutoff review](watchdog-output-boundary.md).

The proposed hardware uses TPS3430 SET0 from buffered `MOTOR_REQUEST_N`, SET1 grounded, a 120 pF C0G timing capacitor and a TPS3808 reset stretcher. Request HIGH both disables supervision and forces driver nSLEEP LOW. Request LOW enables supervision and wakes the driver, so arming must keep IN1/IN2 at `00` until the first checked heartbeat. GPIO17 remains available for the charger interrupt. [TPS3430 timing and enable behavior](https://www.ti.com/lit/ds/symlink/tps3430.pdf), [TPS3808 reset behavior](https://www.ti.com/lit/ds/symlink/tps3808.pdf)

## Future board-driver ownership

One control task owns the policy, GPIO16 WDI, GPIO20 request and motor outputs. It must use a local monotonic microsecond clock. The portable `Cycle.healthy` is an assertion by that task after checking reference, pack/driver/current state, command lease and the actual bounded output operation. It is not a replacement for those checks or proof of their hardware inputs.

1. Begin with request HIGH, WDI HIGH and IN1/IN2 `00`. On an actual reset construct a fresh policy with a new nonzero boot identity; never restore an active session. Disable physical outputs before initializing the software object.
2. Call `arm` only after confirming those levels and a healthy preflight sample no older than 10 ms. The request is bound to this boot and a new nonzero command sequence. Acceptance permits lowering request; it does **not** permit PWM. On the same task, lower the request and call `request_applied` with the current timestamp after the write, within 100 µs of `arm`. This starts the driver wake wait after the physical assertion; GPIO-write latency cannot shorten it. A failed or delayed operation cancels the arm and raises request.
3. Supply a fresh, distinct healthy iteration while IN1/IN2 remain `00`. The first falling-edge request is withheld until more than 1 ms has elapsed from request assertion. This exceeds the TPS3430's 150 µs enable setup and the DRV8874's specified 1 ms maximum wake time. The wake figure is specified under the datasheet's stated test conditions; qualify it on our 3.3 V gate implementation. The watchdog's first pulse does not have a lower-window requirement. [DRV8874 electrical characteristics](https://www.ti.com/lit/ds/symlink/drv8874.pdf)
4. If `cycle` returns true, the same task writes WDI LOW, holds it for a deliberately bounded interval of at least 1 µs, then restores HIGH. This exceeds the watchdog's 50 ns minimum input pulse. No peripheral pulse train, timer callback, ISR, network worker or idle task may perform this feed. The GPIO adapter must complete the pulse and call `edge_applied` within 100 µs of the policy request, using its current timestamp after the write. A failed write or a missed budget raises request and prohibits PWM. The policy cannot observe the real pin; board tests must establish that a successful write produces the expected edge.
5. Only successful first-edge acknowledgement permits PWM. Later edges require at least two new healthy control iterations since the previous feed. At a 10 ms control period this gives approximately 20 ms falling-edge intervals. Enforce strictly **more than 10 ms and less than 45 ms**; no catch-up pulse is generated after a missed deadline. `advance` can only inspect deadlines and stop the session, never feed it. The 100 µs acknowledgement budget must remain inside the physical timing margin.
6. Stop by raising request first, which gates nSLEEP and disables the watchdog. Then put the PWM outputs in their defined inactive state and keep WDI HIGH. Notify the policy with `stop`. Its command sequence remains consumed, so a duplicate cannot rearm. A fault is latched in the policy; ordinary stop/arm calls cannot clear it. Hardware reset creates a new boot-bound policy and requires renewed physical-reference/readiness validation.

`request_n_high()` is true in idle/fault, `pwm_allowed()` is false during arming, and the resting WDI level is always HIGH. Apply safe outputs after every policy failure. If the task never runs again, those software calls cannot help; the external watchdog/reset/gate is the independent cutoff. A firmware policy test therefore cannot establish a 100 ms physical stop time.

## Verification

The existing firmware CMake/CTest command now includes `heartbeat_tests`. It covers default levels, invalid/stale/future preflight, wrong boot/duplicate command, setup and wake boundaries, request-write acknowledgement/latency, no PWM before edge acknowledgement, strict lower/upper feed bounds, two distinct fresh iterations, stale/repeated samples, health faults, late pulse acknowledgement, clock reversal/wrap, no background or catch-up feed, explicit stop/rearm and reboot cancellation. No hardware output or elapsed wall-clock timing is asserted by these tests.
