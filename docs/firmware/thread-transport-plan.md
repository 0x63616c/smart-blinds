# Thread transport implementation boundary

Status: the host authenticated simulator and HA integration are implemented. A separate [motor-disabled C6 Thread/DTLS target](../../firmware/esp-idf-thread/README.md) cross-builds with bounded secure status/wake resources and two OTA slots; its radio-window policy has host tests. It has not been flashed or joined a network, and host-to-C6 DTLS interoperability is untested. A [native libcoap host adapter](../../integrations/thread_transport/README.md) now passes actual localhost DTLS handshake, seven-peer, encrypted-record replay/corruption and wake-lifecycle tests; its peer uses libcoap, and CCM8 requires an explicit OpenSSL security-policy exception that remains an open production decision. Authenticated clock assessment and source-stamped readiness now have [portable policies, host interoperability tests and motor-disabled C6 resources](clock-qualification.md); the C6 additions await a fresh cross-build and the oscillator model remains unvalidated. Provisioning, radio movement messages and OTA delivery are still unimplemented. This does not claim a measured final radio architecture. The C6 module preserves Thread and Wi-Fi options.

## C6 sleepy device path

Use an ESP-IDF 5.5.4 standalone OpenThread node on the C6's native 802.15.4 radio. Build it as a minimal end device, disable router eligibility, use `RxOnWhenIdle=false` and start with a 1000 ms parent poll experiment. Initialize eventfd, NVS, the event loop and the OpenThread stack, attach the netif if using IP sockets, then run the OpenThread main loop in its own task. Calls from other tasks must hold the OpenThread lock. The board/control task must not block on that lock or network I/O. [Espressif OpenThread application guide](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-guides/openthread.html)

The poll period controls an associated sleepy end device's data retrieval. During preparation/movement it must use an awake receiving mode and frequent supervision; test the exact IDF-bundled API and parent behavior before relying on mode transitions. Deep sleep is not an associated connected standby mode: it loses running state and invokes the boot/reference policy. No claim of retained PCNT counting or live encoder feedback during deep sleep is made. [OpenThread poll and receiver APIs](https://openthread.io/reference/group/api-link-link), [Espressif sleep modes](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-reference/system/sleep_modes.html)

A powered Thread parent must support seven children with acceptable queue/retry behavior. The border router supplies IPv6 routing to the separate local coordinator. Confirm the owner's HomePod model and network credentials; HomePod mini/2nd generation are listed by HA, but an unspecified HomePod is not proof. Custom Thread packets need our bridge/integration and commissioning workflow. They do not automatically become Matter or HomeKit devices. [Home Assistant Thread](https://www.home-assistant.io/integrations/thread/)

## Wake, authenticate, synchronize, then move

The proposed sequence separates idle wake latency from the strict motion-command lifetime:

1. A fresh HA request creates a short-lived coordinator intent in memory. Send a **wake solicitation** to every member. This can only request a temporary awake/authentication window; it cannot enable the motor, prepare a trajectory or restore position. Bound retries and the awake window to avoid battery drain. A new session challenge and rate limiting must prevent replayed wake traffic from holding the receiver on.
2. Each node wakes on its parent poll, proves its boot identity and establishes an authenticated fresh session. Perform challenge-bound four-timestamp clock exchanges while awake. Use a conservative offset interval including asymmetric delay, scheduling jitter and subsequent oscillator drift; an arbitrary midpoint alone is not an error bound. Refuse coordinated motion if absolute clock error exceeds 10 ms. Clock-quality timeouts return to idle without movement.
3. Request a new readiness snapshot: reference/calibration revision, physical height, healthy pack/charger/driver, speed capability and actual sample time. Boot changes, a stale snapshot or any unavailable member reject the whole intent. There is no stale fallback to last-known position.
4. Only once all nodes are awake and clock-qualified call the existing `begin_group`. Its current schedule is start in 3000 ms, ready acknowledgments by 1700 ms and commit acknowledgments by 2500 ms. A prepare/commit packet expires after 250 ms; **do not put these packets into a one-second sleepy queue**. Every member must be committed before the coordinator issues running leases. The initial wake/sync time adds to the three-second lead; total user latency must be measured and the user-facing 'few seconds' budget revisited if needed.
5. Stay awake through the move. Send active source-stamped reports at most 100 ms apart; the coordinator stops peers on reports older than 250 ms. Renew a 300 ms local lease every 100 ms. A locally expired lease disables movement even if STOP is lost. Network APIs, flash and the pack reader run outside the motor timing task.
6. Completion requires fresh measured arrival from every member. Cancel the session's movement capability after completion/abort, publish final position and return to sleepy operation. Retain no movement request across a bridge restart, device reboot, reconnect or update. A button STOP interrupts the device immediately and notifies peers; a failed radio link still leaves local stop authority.

This is a protocol engineering proposal. Thread does not itself prove synchronized motion, a 5 mm tracking limit or all-member atomic execution. A partition can let some committed nodes receive leases and others fail to start; active supervision detects this and aborts. At 30 mm/s, a 300 ms lease allows up to 9 mm of travel plus the physical stopping distance after the final renewal. The normal 5 mm alignment target is separate from this fault excursion.

## Authentication implemented on the host

`integrations/bridge/auth.py` bounds a packet to 1200 bytes and uses a binary header: version, direction, 16-byte session, uint64 boot, uint64 sequence, uint64 send time, payload length. A domain/device-bound HMAC-SHA256 covers the header and finite JSON payload. Receiving checks MAC before parsing, exact length/session/boot/direction, strictly increasing packet counter, conservative age and a maximum 10 ms clock-error bound. Invalid packets cannot advance the receive counter. Command sequence/idempotence remains a separate node-control concern. Retransmission must use a fresh packet counter while retaining the same command identity.

The fixture generates separate random keys and sessions per virtual node; keys never leave memory. This demonstrates codec/contract behavior, not secure deployment. HMAC authenticates but does not encrypt; Thread network encryption alone does not supply the application's per-device authorization boundary. Before a hardware release, choose and review a standard secure session transport (for example DTLS with provisioned per-device identities), onboarding/rotation/revocation, encrypted credential storage and boot/session negotiation. Do not blindly promote this fixture codec into a custom production cryptosystem.

The 1200-byte bound is below IPv6's minimum MTU but can still fragment into many 802.15.4 frames. Compact binary/CBOR active messages, packet count, seven-node airtime and congestion need measurement. Strict C6 message schemas must preserve uint64 integers exactly; converting boot IDs through floating-point JSON loses identity bits.

## Commissioning, updates and acceptance

Provision network membership and per-device credentials through a deliberate local commissioning flow, with physical access and a short pairing window. Never commit a Thread dataset, install code or secret into source, default firmware or logs. A HomePod/Apple network may require a supported credential-transfer path; its existence alone is insufficient. Custom Thread is not HA Matter onboarding. If later choosing Matter, HA currently documents update limitations with Apple border routers, so retain a verified wired recovery/update path. [HA Matter update limitations](https://www.home-assistant.io/integrations/matter/#matter-ota-device-updates)

The initial full radio stack cross-build now fits two OTA slots in the selected 4 MB flash; final application fit must be rechecked as features are added. Before a real radio release, prove signed update/rollback and watchdog behavior, then measure one/seven-node idle energy, worst-case wake/start latency, clock-bound validity, packet loss/congestion, parent restart, coordinator restart and physical-button interruption. Motor/gauge/encoder work must stay disabled until the real board interface and pack profile pass their own bring-up. Current host tests and the motor-disabled C6 builds do not satisfy these acceptance steps.
